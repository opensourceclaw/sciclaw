## 1. Gate System Design

### 1.1 Overview

The Gate System enforces quality checkpoints before pipeline progression. It was modeled after DevClaw v7.0.0-rc.7's Gate architecture.

### 1.2 File Breakdown

#### `src/gate/types.ts`

**Purpose**: Core type definitions for the Gate system.

**Type Hierarchy**:

```
GateStatus (union type)
├── "pending"    — Gate not yet evaluated
├── "passed"     — Gate passed all checks
├── "failed"     — Gate blocked by critical issue
└── "blocked"    — Gate waiting on dependency

GateState (interface)
├── gateId: string        — Unique identifier
├── status: GateStatus    — Current status
├── timestamp: number     — Last update time
└── metadata: object      — Arbitrary context

InternalVerifySubmission (interface)
├── pipelineId: string
├── version: string
├── typeCheck: TypeCheckResult
├── build: BuildResult
├── tests: TestResult
├── regression: RegressionResult
├── qualityChecks: QualityChecks
├── configValid?: boolean
└── dependenciesValid?: boolean
```

**Design Decision**: Used `type` over `interface` for unions (`GateStatus`) and `interface` for objects with many properties. This follows TypeScript best practices for discriminated unions.

**Alternative Considered**: Enums for `GateStatus`. Rejected because:
- String literals provide better debug output
- No need for numeric values
- JSON serialization is cleaner

---

#### `src/gate/GateRegistry.ts`

**Purpose**: Centralized gate status management with persistence.

**Class Design**:

```typescript
class GateRegistry {
  private gates: Map<string, GateState>      // In-memory state
  private listeners: StatusChangeCallback[]  // Observer pattern
  private gatesDir: string                   // Persistence path

  getGateStatus(gateId): GateStatus
  setGateStatus(gateId, status, metadata?)
  validateAllGates(): ValidationResult
  onStatusChange(callback)
  getAllGates(): GateState[]
  reset()
}
```

**Persistence Strategy**:

| Decision | Rationale |
|----------|-----------|
| **Filesystem** | No external database dependency; works offline; portable |
| **JSON format** | Human-readable; easy debugging; git-diffable |
| **Location** | `~/.deepclaw/gates/gates.json` — follows XDG conventions |
| **Sync writes** | Simplicity; gates are low-frequency updates |

**Error Handling**: Persistence failures are silently caught — gate state is in-memory first, persistence is best-effort backup.

**Alternative Considered**: SQLite. Rejected because:
- Adds dependency
- Overkill for <100 gates
- JSON is sufficient for current scale

---

#### `src/gate/gates/InternalVerifyGate.ts`

**Purpose**: Enforce verification rules before pipeline can proceed.

**Class Design**:

```typescript
class InternalVerifyGate {
  private readonly gateId: string
  private readonly registry: GateRegistry

  async submit(submission): Promise<void>  // Throws on failure
  validate(submission): VerifyResult       // Returns result
  markAsVerified(submission, verifier, comments?)
  markAsRejected(submission, issues)
  getStatus(): GateStatus
}
```

**9 Rules Rationale**:

| Rule | Type | Why |
|------|------|-----|
| `type_check_failed` | Failed | TypeScript errors = broken code |
| `build_failed` | Failed | Can't run broken builds |
| `tests_failed` | Failed | Failing tests = bugs |
| `incomplete_tests` | Failed | Skipped tests = hidden failures |
| `regression_failed` | Failed | Fewer tests = deleted coverage |
| `config_error` | Failed | Invalid config = runtime errors |
| `chinese_characters_detected` | Warning | Style issue, not functional |
| `hardcoded_paths_detected` | Warning | Portability issue |
| `missing_apache_headers` | Warning | Compliance issue |

**6 Failed + 3 Warning Split**:
- **Failed rules**: Block pipeline, must be fixed
- **Warning rules**: Informational, don't block

This follows the principle: "Block only what breaks, warn what could be better."

**Alternative Considered**: All 9 rules as blocking. Rejected because:
- Chinese characters in source don't break functionality
- Would be overly strict for incremental adoption

## 2. Pipeline CLI Design

### 2.1 Overview

The Pipeline CLI provides command-line control for research workflows. It follows a coordinator-based architecture with persistent state.

### 2.2 File Breakdown

#### `src/cli/types.ts`

**Purpose**: Type definitions for pipeline state management.

**Key Types**:

```typescript
enum PipelineStage {
  PLAN = "plan",
  SEARCH = "search",
  SYNTHESIZE = "synthesize",
  WRITE = "write",
  VERIFY = "verify",
}

type PipelineStatus = "pending" | "running" | "paused" | "completed" | "failed"

interface PipelineState {
  id: string
  topic: string
  status: PipelineStatus
  currentStage: PipelineStage
  createdAt: number
  updatedAt: number
  stages: StageState[]
}
```

**5 Stages Rationale**:

| Stage | Purpose | Output |
|-------|---------|--------|
| PLAN | Decompose query | Sub-queries |
| SEARCH | Execute searches | Raw results |
| SYNTHESIZE | Combine findings | Synthesized content |
| WRITE | Generate report | Markdown/HTML/PDF |
| VERIFY | Quality check | Verification result |

**Alternative Considered**: 3 stages (PLAN → EXECUTE → VERIFY). Rejected because:
- Too coarse-grained
- No checkpoint for synthesis quality
- Doesn't match DeepClaw's multi-agent flow

---

#### `src/cli/pipeline-coordinator.ts`

**Purpose**: State machine for pipeline lifecycle management.

**Class Design**:

```typescript
class PipelineCoordinator {
  private pipelinesDir: string

  create(topic, config?): PipelineState
  get(id): PipelineState | null
  getLatest(): PipelineState | null
  listAll(): string[]
  start(id): PipelineState | null
  advance(id): PipelineState | null
  approve(id, stage): PipelineState | null
  fail(id, reason): PipelineState | null
  delete(id): boolean
}
```

**State Machine**:

```
[pending] --start()--> [running]
     │                      │
     │                      ├── advance() --> [running] (next stage)
     │                      │
     │                      └── fail() --> [failed]
     │
     └── final advance() --> [completed]
```

**Persistence**: `~/.deepclaw/pipelines/{id}.json`
- One file per pipeline (vs single file for all)
- Enables concurrent pipeline management
- Easy cleanup by file deletion

---

#### `src/cli/pipeline.ts`

**Purpose**: CLI entry point using Commander.js.

**Why Commander**:

| Framework | Pros | Cons | Verdict |
|-----------|------|------|---------|
| **commander** | Simple, popular, good docs | Slightly verbose | ✅ Selected |
| yargs | Powerful, flexible | Complex API | Overkill |
| plain argv | Zero deps | Manual parsing | Too manual |

**Command Structure**:

```bash
deepclaw pipeline <subcommand> [args] [options]
```

**Subcommands**:

| Command | Args | Options |
|---------|------|---------|
| create | topic | --sources, --format |
| start | pipeline-id | — |
| status | [pipeline-id] | --json |
| approve | pipeline-id stage | — |
| verify | pipeline-id | — |
| list | — | — |
| delete | pipeline-id | — |

---

#### `src/cli/commands/start.ts`

**Design**:
- Creates pipeline with UUID
- Prints next steps guidance
- Does NOT auto-start (explicit start required)

**Error Handling**: None at command level — exceptions bubble to Commander.

---

#### `src/cli/commands/status.ts`

**Design**:
- No args: list all pipelines
- With args: show detailed status
- `--json`: machine-readable output

**Icon Convention**:
- ✓ completed
- → running
- ✗ failed
- ○ pending

---

#### `src/cli/commands/approve.ts`

**Design**:
- Validates stage is current
- Calls `coordinator.approve()`
- Prints new state

**Error Handling**: `process.exit(1)` on:
- Pipeline not found
- Stage mismatch
- Coordinator error

---

#### `src/cli/commands/verify.ts`

**Design**:
- Creates InternalVerifyGate instance
- Submits default verification (placeholder)
- Integrates Gate with Pipeline

**Future**: Will submit real test/build results once integrated with orchestrator.

### 2.3 Design Decisions

#### Why `process.exit(1)` for CLI Errors

| Approach | Pros | Cons |
|----------|------|------|
| `process.exit(1)` | Simple, clear exit code | Abrupt termination |
| Throw exception | Stack trace | Uncaught exception |
| Return error code | Clean | Requires tracking |

**Decision**: `process.exit(1)` because:
- CLI context — immediate feedback needed
- Clear exit code for scripting
- Stack traces not useful for users

## 3. Chinese Removal Strategy

### 3.1 Affected Files

| File | Chinese Content | Resolution |
|------|-----------------|------------|
| `src/synthesis/discovery_engine.ts` | Keywords for topic detection | Removed Chinese keywords |
| `src/synthesis/cross_domain_synthesizer.ts` | Regex patterns | Removed Chinese patterns |
| `src/synthesis/iterative_verifier.ts` | Stopwords, patterns | Removed Chinese stopwords |
| `src/multimodal/chart.ts` | Chart type names | Removed Chinese names |
| `src/tools/site_specific.ts` | "知乎" in regex | Changed to "Zhihu" |
| `src/llm/providers/qwen.ts` | "通义千问" in comment | Changed to "Qwen" |

### 3.2 Translation Approach

**Rule**: Only translate code/comments, not user-facing functionality.

| Type | Action |
|------|--------|
| Chinese keywords in arrays | Remove (English keywords sufficient) |
| Chinese in regex patterns | Remove (English patterns cover use case) |
| Chinese stopwords | Remove (Chinese text not primary target) |
| Proper nouns (知乎, 通义千问) | Transliterate to English |

**Why not i18n**: DeepClaw source code is English-only by policy. User-facing strings would need i18n, but current Chinese was in detection patterns, not UI.

### 3.3 CI Check Script

**File**: `scripts/check-chinese.sh`

```bash
#!/bin/bash
CHINESE_FILES=$(find src -name "*.ts" -exec grep -l '[\u4e00-\u9fff]' {} \;)
if [ -n "$CHINESE_FILES" ]; then
    echo "❌ Chinese characters found"
    exit 1
fi
echo "✅ No Chinese characters"
exit 0
```

**Design**:
- Runs on `src/**/*.ts` only (not tests/docs)
- Exit 1 on failure (CI blocking)
- Simple regex, no dependencies

## 4. Design Decisions & Trade-offs

### 4.1 Gate is Standalone (Not Integrated into Orchestrator)

**Current State**: Gate and Orchestrator are separate modules.

**Rationale**:
- Phase 1 focused on Gate foundation
- Integration requires Orchestrator refactor
- Separation allows independent testing

**Future**: v3.6.0 will integrate Gate checks into `ResearchStateMachine` transitions.

---

### 4.2 JSON File Persistence vs Database

**Decision**: JSON files in `~/.deepclaw/`

**Trade-offs**:

| Aspect | JSON Files | Database |
|--------|------------|----------|
| Dependencies | None | SQLite/Postgres |
| Setup | Zero config | Requires migration |
| Query speed | O(n) scan | O(log n) indexed |
| Concurrent access | Not safe | Safe |
| Debugging | `cat file.json` | SQL queries |

**Decision**: JSON files because:
- <100 gates/pipelines expected
- No concurrent access needed
- Zero configuration
- Easy debugging

---

### 4.3 Commander vs yargs

**Decision**: Commander

**Trade-offs**:

| Aspect | Commander | yargs |
|--------|-----------|-------|
| Learning curve | Low | Medium |
| Bundle size | Small | Larger |
| Subcommands | Native | Requires setup |
| Ecosystem | Large | Large |

**Decision**: Commander because:
- Simpler API
- Native subcommand support
- Sufficient for 7 commands

---

### 4.4 6 Failed + 3 Warning Rules

**Decision**: Split rules into blocking (failed) and non-blocking (warning).

**Trade-offs**:

| Approach | Pros | Cons |
|----------|------|------|
| All blocking | Strict quality | May block valid work |
| All warning | Never blocks | No enforcement |
| **Split** | Balanced | More complex |

**Decision**: Split because:
- Chinese characters don't break functionality
- Hardcoded paths are portability issues, not bugs
- Missing headers are compliance, not correctness

## 5. Alternative Approaches Considered

### 5.1 Gate as Decorator Pattern

**Idea**: Use TypeScript decorators on methods to enforce gates.

**Rejected because**:
- Requires experimental decorators
- Harder to test in isolation
- Less explicit than imperative checks

### 5.2 Pipeline as Event Emitter

**Idea**: Pipeline emits events on stage transitions.

**Rejected because**:
- Over-engineering for current needs
- State machine is simpler
- Can add later if needed

### 5.3 Chinese Detection at Build Time

**Idea**: TypeScript plugin that errors on Chinese characters.

**Rejected because**:
- Slows down compilation
- CI script is sufficient
- No need for IDE-time feedback
