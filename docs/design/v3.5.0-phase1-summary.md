## 2. Component Design

### 2.1 Gate Enforcement System

**Context**: `src/gate/` already has skeleton code from a previous iteration. Need to complete and integrate.

**Existing files** (keep, enhance):
```
src/gate/
├── index.ts                    # ✅ Exports (complete)
├── types.ts                    # ✅ Types (complete)
├── GateRegistry.ts             # ✅ Registry + persistence (complete)
└── gates/
    ├── index.ts                # ✅ Exports (complete)
    └── InternalVerifyGate.ts   # ✅ 9 validation rules (complete)
```

**What's missing — integration points**:

| Integration | Where | What |
|-------------|-------|------|
| **Gate → Orchestrator** | `src/agents/orchestrator.ts` | Inject Gate check before each phase transition |
| **Gate → Pipeline CLI** | `src/cli/pipeline-coordinator.ts` | Gate status check in `verify` command |
| **Gate tests** | `tests/gate/` | 12+ unit tests for InternalVerifyGate |

**Design Decision**: Gate is NOT a new pipeline stage. Instead, it's a cross-cutting concern injected into the existing orchestrator's phase-transition logic. This keeps the research pipeline simple while adding enforcement.

**Integration Pattern**:
```
Orchestrator.executePlan()
  └── for each phase:
        ├── checkGate(phase)        ← NEW: Gate injection
        ├── dispatch tasks to agents
        └── record results
```

**InternalVerifyGate Rules** (already implemented, 9 rules):
- 6 Failed (block): type_check, build, tests, incomplete_tests, regression, config_error
- 3 Warning (don't block): chinese_chars, hardcoded_paths, missing_apache_headers

**Pipeline Stages**: PLAN → SEARCH → SYNTHESIZE → WRITE → VERIFY

**Commands**:
