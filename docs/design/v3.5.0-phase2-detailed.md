## 1. Monitoring Observer

### 1.1 Overview

The Monitoring Observer collects research-domain metrics and emits alerts when thresholds are exceeded. Unlike DevClaw's build-focused metrics, DeepClaw's metrics are specific to research workflows.

**Key Design Principle**: Observer is **passive** — it collects metrics and emits alerts but does **not** block the pipeline.

#### `src/monitoring/Observer.ts`

**Purpose**: Central observer that collects metrics and manages alerts.

**Class Design**:

```typescript
import type {
  ResearchMetrics,
  Alert,
  ObserverConfig,
  MetricsSnapshot,
  MonitoringStatus,
} from "./types.js";
import { AlertManager } from "./AlertManager.js";
import { MetricsCollector } from "./MetricsCollector.js";

export type MetricsHandler = (snapshot: MetricsSnapshot) => void;
export type AlertHandler = (alert: Alert) => void;

/**
 * DeepClaw Observer for research pipeline monitoring.
 * 
 * Design Principle: Passive observer — collects metrics without blocking pipeline.
 */
export class DeepClawObserver {
  private config: ObserverConfig;
  private alertManager: AlertManager;
  private metricsCollector: MetricsCollector;
  private metricsHandlers: Set<MetricsHandler> = new Set();
  private alertHandlers: Set<AlertHandler> = new Set();
  private startTime: number;
  private currentPipelineId: string | null = null;

  constructor(config?: Partial<ObserverConfig>);

  // ── Lifecycle Hooks (called by Orchestrator) ──────────────────────

  /** Called when research starts. */
  onResearchStart(pipelineId: string, topic: string): void;

  /** Called when research ends. */
  onResearchEnd(pipelineId: string, success: boolean): ResearchMetrics;

  // ── Per-Phase Hooks ───────────────────────────────────────────────

  /** Called when a phase starts. */
  onPhaseStart(phaseName: string): void;

  /** Called when a phase ends. */
  onPhaseEnd(phaseName: string, durationMs: number): void;

  // ── Per-Agent Hooks ───────────────────────────────────────────────

  /** Called when an agent starts processing. */
  onAgentStart(role: string): void;

  /** Called when an agent finishes processing. */
  onAgentEnd(role: string, durationMs: number, status: "success" | "failed" | "partial"): void;

  // ── Search Hooks ───────────────────────────────────────────────────

  /** Called when search completes. */
  onSearchResult(query: string, resultCount: number, cacheHit: boolean): void;

  // ── Token Tracking ─────────────────────────────────────────────────

  /** Record token usage. */
  recordTokenUsage(tokens: number): void;

  // ── Metrics Access ──────────────────────────────────────────────────

  /** Get current metrics. */
  getMetrics(): ResearchMetrics;

  /** Get metrics snapshot. */
  getSnapshot(): MetricsSnapshot;

  /** Get metrics history. */
  getHistory(limit?: number): MetricsSnapshot[];

  // ── Alert Management ────────────────────────────────────────────────

  /** Get active alerts. */
  getAlerts(): Alert[];

  /** Subscribe to metrics updates. */
  onMetrics(handler: MetricsHandler): void;

  /** Subscribe to alerts. */
  onAlert(handler: AlertHandler): void;

  // ── Status ──────────────────────────────────────────────────────────

  /** Get monitoring status. */
  getStatus(): MonitoringStatus;

  /** Reset observer state. */
  reset(): void;
}
```

**Integration Points with Orchestrator**:

| Orchestrator Method | Observer Hook |
|---------------------|---------------|
| `executePlan()` start | `onResearchStart(pipelineId, topic)` |
| `executePlan()` end | `onResearchEnd(pipelineId, success)` |
| Phase execution start | `onPhaseStart(phase.name)` |
| Phase execution end | `onPhaseEnd(phase.name, durationMs)` |
| `dispatchTask()` start | `onAgentStart(role)` |
| `dispatchTask()` end | `onAgentEnd(role, durationMs, status)` |

**Error Handling**: Observer hooks never throw. Errors are logged and ignored to prevent pipeline disruption.

### 1.3 Design Decisions

#### Why Passive Observer

| Approach | Pros | Cons |
|----------|------|------|
| **Passive (selected)** | No pipeline blocking, safe failure | Can't auto-remediate |
| Active (blocking) | Can stop bad pipelines | Single point of failure |

**Decision**: Passive because:
- Research pipelines are long-running; blocking is disruptive
- Alerts can be handled externally
- Observer failures shouldn't affect pipeline

#### Why Filesystem Persistence

| Approach | Pros | Cons |
|----------|------|------|
| **Filesystem (selected)** | Zero deps, portable, debuggable | No indexing |
| SQLite | Indexed queries | External dependency |
| In-memory only | Fast | Lost on restart |

**Decision**: Filesystem because:
- <1000 metrics snapshots expected
- JSON is human-readable
- No external dependencies
- Easy backup/restore

---

### 1.4 Error Handling Strategy

| Error Type | Handling |
|------------|----------|
| Hook failure | Log and continue (never throw) |
| Persistence failure | Log and continue (in-memory fallback) |
| Invalid metric value | Ignore, use default |
| Alert evaluation error | Skip rule, log error |

**Pattern**: All observer methods wrapped in try-catch:

```typescript
onResearchStart(pipelineId: string, topic: string): void {
  try {
    this.metricsCollector.startSession(pipelineId);
  } catch (err) {
    // Log but don't throw — observer must not block pipeline
    console.error("Observer error:", err);
  }
}
```

## 2. Human-in-the-Loop Approval

### 2.1 Overview

The Approval Flow enables human review of critical decisions in the research pipeline. It integrates with the existing Gate system.

**Key Design Principle**: **Timeout ≠ approval** — silence is not consent.

#### `src/approval/ApprovalGate.ts`

**Purpose**: Gate integration with existing GateRegistry.

**Class Design**:

```typescript
import { GateRegistry } from "../gate/GateRegistry.js";
import type { GateStatus } from "../gate/types.js";
import type { ApprovalRequest, ApprovalResult, ApprovalPoint } from "./types.js";
import { ApprovalFlow } from "./ApprovalFlow.js";

/**
 * Approval gate that integrates with the Gate system.
 * 
 * Design Decision: ApprovalGate uses existing GateRegistry for consistency
 * with InternalVerifyGate pattern.
 */
export class ApprovalGate {
  private readonly gateId: string;
  private readonly registry: GateRegistry;
  private readonly approvalFlow: ApprovalFlow;

  constructor(registry: GateRegistry, approvalFlow: ApprovalFlow, gateId?: string);

  /**
   * Check if approval is required and process accordingly.
   * Returns true if approved, false if rejected/pending.
   */
  async check(point: ApprovalPoint, pipelineId: string, context: Record<string, unknown>): Promise<boolean>;

  /**
   * Request approval for a decision.
   * Blocks until decision is made or timeout.
   */
  async requestApproval(
    point: ApprovalPoint,
    pipelineId: string,
    title: string,
    description: string,
    context: Record<string, unknown>
  ): Promise<ApprovalResult>;

  /**
   * Process human decision.
   */
  processDecision(requestId: string, decision: "approve" | "reject", decidedBy: string, reason?: string): void;

  /**
   * Get gate status.
   */
  getStatus(): GateStatus;

  /**
   * Mark gate as passed.
   */
  markApproved(requestId: string, approver: string): void;

  /**
   * Mark gate as failed.
   */
  markRejected(requestId: string, reason: string): void;
}
```

**Integration with GateRegistry**:

```typescript
// ApprovalGate follows same pattern as InternalVerifyGate
constructor(registry: GateRegistry, approvalFlow: ApprovalFlow, gateId?: string) {
  this.registry = registry;
  this.gateId = gateId ?? "approval";
  this.approvalFlow = approvalFlow;
  this.registry.setGateStatus(this.gateId, "pending");
}

markApproved(requestId: string, approver: string): void {
  this.registry.setGateStatus(this.gateId, "passed", {
    requestId,
    approver,
    approvedAt: Date.now(),
  });
}
```

### 2.4 Design Decisions

#### Why Timeout ≠ Approval

| Approach | Pros | Cons |
|----------|------|------|
| Timeout = approve | Faster | Silence might be oversight |
| **Timeout = configurable** | Explicit consent required | May block pipeline |

**Decision**: Configurable because:
- Research decisions are important; should be explicit
- Budget approvals should never auto-approve
- Plan approvals can auto-approve if timeout is intentional

#### Why File-Based Approval

| Approach | Pros | Cons |
|----------|------|------|
| **File-based (selected)** | Persistent, auditable, async | Requires file system access |
| CLI prompt | Interactive, immediate | Blocks terminal, no audit |
| HTTP endpoint | Remote access | Requires server |

**Decision**: File-based because:
- Works in async/automated contexts
- Full audit trail
- Can be processed by external tools
- No additional infrastructure

#### How Audit Logging Works

```typescript
// Every decision is logged with timestamp
interface ApprovalAuditEntry {

  requestId: string;
  action: "created" | "approved" | "rejected" | "timeout";
  point: ApprovalPoint;
  pipelineId: string;

  reason?: string;
```

## 3. Alternative Approaches Considered

### 3.1 Observer as Event Emitter

**Idea**: Observer extends Node's EventEmitter.

**Rejected because**:
- Unnecessary complexity for 2 event types
- Set<Handler> pattern is simpler
- No need for event namespacing

### 3.2 Approval via Message Queue

**Idea**: Use Redis/RabbitMQ for approval requests.

**Rejected because**:
- Adds external dependency
- File-based is sufficient for expected scale
- Simpler deployment

### 3.3 Real-time Dashboard

**Idea**: WebSocket-based metrics dashboard.

**Rejected because**:
- Out of scope for v3.5.0
- Can be added later
- File-based metrics enable external tools

```typescript
class Orchestrator {
  private observer?: DeepClawObserver;
  private approvalGate?: ApprovalGate;

  async executePlan(plan: OrchestrationPlan): Promise<OrchestrationResult> {
    // Observer: start

    // Approval: check research plan
    if (this.approvalGate) {
      const approved = await this.approvalGate.check("research_plan", plan.id, { plan });
      if (!approved) {
        return { ...result, overallStatus: "rejected" };
      }
    }

    // ... phase execution with observer hooks ...

    // Observer: end

    return result;
  }
}
```
