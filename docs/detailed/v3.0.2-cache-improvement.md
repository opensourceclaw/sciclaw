## 1. 现状分析

### 1.1 当前实现

| 项目 | 详情 |
|------|------|
| 文件 | `src/cache/index.ts` (116 行) |
| 类型 | `SearchCache` — LRU + TTL，内存 Map |
| 命中率 | ~50%（估算） |
| 淘汰策略 | FIFO（Map 插入顺序），非真正 LRU |
| TTL | 默认 3600s，全局统一 |
| 容量 | 默认 100 条 |
| 并发 | 无分布式支持 |
| 可观测性 | `stats()` 仅返回 size/maxSize/ttl |

### 1.2 使用点

| 文件 | 调用方式 | 用途 |
|------|---------|------|
| `src/search/index.ts` | `getCache()` 全局单例 | 搜索结果缓存 |
| `src/validation/factcheck_service.ts` | 自建 Map（独立实现） | 事实核查结果缓存 |
| `src/deepclaw/cache.py` | Python 侧独立 Cache 类 | Python 工具层缓存 |

**问题**：TypeScript 侧存在两套独立缓存实现，缺乏统一管理。

### 1.3 根因分析（命中率低）

1. **无预热**：首次查询必定 miss，冷启动体验差
2. **统一 TTL**：搜索结果（短期有效）和事实核查（长期有效）共用相同 TTL
3. **淘汰粗糙**：FIFO 可能淘汰高频热点数据
4. **无压缩**：大结果集占用大量内存，限制了可缓存条目数
5. **无可观测性**：无法追踪命中率、延迟节省等指标，缺少优化依据

## 4. Module 2: Cache Invalidation

### 4.1 失效策略

```typescript
// src/cache/types.ts

export type InvalidationStrategy = 
  | "ttl"           // 仅基于时间
  | "topic_aware"   // 基于主题（同类查询共用一个失效窗口）
  | "source_aware"  // 基于来源（不同搜索引擎不同 TTL）
  | "adaptive";     // 自适应（根据命中模式动态调整）

export interface InvalidationConfig {
  strategy: InvalidationStrategy;  // 默认 "adaptive"
  defaultTTL: number;              // 默认 3600s
  sourceTTLs: Partial<Record<SearchEngine, number>>; // 来源级别 TTL
  topicWindowMs: number;           // 主题窗口，默认 1800000 (30min)
  minTTL: number;                  // 自适应下限，默认 300
  maxTTL: number;                  // 自适应上限，默认 86400
}
```

### 4.2 实现要点

```typescript
// src/cache/invalidation.ts

export class InvalidationManager {
  constructor(private config: InvalidationConfig) {}

  /** 计算给定条目的 TTL */
  computeTTL(params: {
    query: string;
    engines: SearchEngine[];
    accessCount: number;       // 该 key 的历史访问次数
    lastAccessGapMs: number;   // 距上次访问的间隔
  }): number {
    // adaptive: 高频 key TTL 缩短（数据应更新鲜），低频 key TTL 延长（减少重复查询）
    // source_aware: DuckDuckGo 较稳定 → 长 TTL，Google 实时性强 → 短 TTL
    // topic_aware: 同类查询共享失效窗口
  }

  /** 主题提取（简单规则） */
  extractTopic(query: string): string { /* 关键词匹配 + 小写规范化 */ }

  /** 批量失效 */
  invalidateByTopic(topic: string): void { /* 通知 cache 清理 */ }
  invalidateBySource(source: string): void { /* 通知 cache 清理 */ }
}
```

### 4.3 自适应 TTL 算法

```
baseTTL = defaultTTL (3600s)

// 访问频率因子：高频访问 → TTL * 0.7
frequencyFactor = accessCount > 5 ? 0.7 : accessCount > 2 ? 0.85 : 1.0

// 间隔因子：长时间未访问 → TTL * 1.3（保留更久）
gapFactor = lastAccessGapMs > 3600000 ? 1.3 : 1.0

// 来源因子
sourceFactor = duckduckgo ? 1.2 : google ? 0.8 : 1.0

finalTTL = clamp(baseTTL * frequencyFactor * gapFactor * sourceFactor, minTTL, maxTTL)
```

### 7.2 实现要点

```typescript
// src/cache/distributed.ts

export class DistributedCache {
  private redis: Redis | null = null;
  private localFallback: SearchCache;
  private healthy = false;

  constructor(
    private config: DistributedCacheConfig,
    localFallback: SearchCache,
  ) {}

  async connect(): Promise<boolean> {
    // 尝试连接 Redis，失败则标记 unhealthy
    // 使用 ioredis 或 redis 包（peer dependency）
  }

  async get(key: string): Promise<SearchResult[] | null> {
    if (this.healthy) {
      try {
        const raw = await this.redis.get(key);
        return raw ? JSON.parse(raw) : null;
      } catch {
        this.markUnhealthy();
      }
    }
    return this.localFallback.get(key); // graceful degradation
  }

  async set(key: string, results: SearchResult[], ttl: number): Promise<void> {
    if (this.healthy) {
      try {
        await this.redis.setex(key, ttl, JSON.stringify(results));
        return;
      } catch {
        this.markUnhealthy();
      }
    }
    this.localFallback.set(key, results); // fallback
  }

  isHealthy(): boolean { return this.healthy; }

  private markUnhealthy(): void {
    this.healthy = false;
    // 定期重连（每 30s 尝试一次）
  }
}
```

### 7.3 依赖策略

`ioredis` 作为可选依赖（`optionalDependencies`），不强制安装。运行时 `try/catch require` 检测。无 Redis 包时 `enabled: true` 也会自动回退本地。

### 7.4 跨进程共享

启用 Redis 后，多个 DeepClaw 实例共享同一缓存空间，大幅降低重复搜索成本。适合服务端部署场景（`src/api/server.ts`）。

## 8. 集成点与数据流

### 8.1 SearchCache 重构

原 `src/cache/index.ts` → 重命名为 `src/cache/search-cache.ts`，内聚所有模块：

```typescript
// src/cache/search-cache.ts

export class SearchCache {
  private cache: Map<string, CacheEntry> = new Map();
  private analytics: CacheAnalytics;
  private invalidation: InvalidationManager;
  private compressor: CacheCompressor;
  private distributed: DistributedCache | null;

  constructor(config: CacheConfig) { /* 组装子模块 */ }

  async get(query: string, engines: string[]): Promise<SearchResult[] | null> {
    const key = this.getKey(query, engines);
    const startTime = Date.now();

    // 1. 优先查 Redis
    if (this.distributed) {
      const result = await this.distributed.get(key);
      if (result) {
        this.analytics.recordHit(key, Date.now() - startTime);
        return result;
      }
    }

    // 2. 本地查询
    const entry = this.cache.get(key);
    if (entry) {
      const ttl = this.invalidation.computeTTL({ query, engines, ... });
      if (Date.now() - entry.timestamp <= ttl) {
        this.analytics.recordHit(key, Date.now() - startTime);
        return this.compressor.decompress(entry.compressedData);
      }
      this.cache.delete(key);
      this.analytics.recordEviction(key);
    }

    this.analytics.recordMiss(key);
    return null;
  }

  set(query: string, engines: string[], results: SearchResult[]): void {
    const key = this.getKey(query, engines);
    const { data } = this.compressor.compress(results);

    // LRU eviction（修复原 FIFO 问题）
    if (this.cache.size >= this.maxSize) {
      this.evictLRU();
    }

    this.cache.set(key, { compressedData: data, timestamp: Date.now(), accessCount: 0 });

    // 同步到 Redis
    this.distributed?.set(key, results, this.invalidation.computeTTL({ ... }));
  }

  getMetrics(): CacheMetrics { return this.analytics.getSnapshot(); }

  private evictLRU(): void {
    // 真正 LRU：遍历找 timestamp 最旧的条目
  }
}
```

## 10. 风险与缓解

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|---------|
| Redis 连接失败导致搜索变慢 | 中 | 中 | 连接超时 ≤2s，自动回退本地；定期重连 |
| 压缩增加 CPU 开销 | 低 | 低 | `minBytesToCompress` 阈值；fast 模式零额外依赖 |
| Analytics 内存泄漏（热点 Map 无限增长） | 低 | 中 | topK 限制 + 周期性 reset |
| 预热阶段并发过高打爆搜索引擎 | 低 | 高 | concurrency 默认 2，可配置；失败隔离 |
| 向后兼容破坏 | 低 | 高 | `getCache()` API 不变；全量回归测试 |

## 附录 A：与 Python 侧的关系

Python 侧 `src/deepclaw/cache.py` 独立维护，本次不改动。两个缓存的边界：
- **TypeScript `SearchCache`**: TS 侧搜索/验证结果缓存（Node.js 运行时）
- **Python `Cache`**: Python CLI 工具层缓存

如需跨语言缓存共享，后续版本可通过 Redis 统一。

## 附录 B：与 claw-mem 的关系

`CacheAnalytics.flush()` 可选写入 claw-mem，使缓存指标跨 Session 持久化，支撑 `CacheWarmer` 的热点自动发现。无需 claw-mem 时本地内存统计仍正常工作。
